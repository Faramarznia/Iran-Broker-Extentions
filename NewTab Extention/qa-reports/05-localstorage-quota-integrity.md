## تست خرابی داده — نتیجهٔ واقعی هر ۱۱ کلید × ۲ حالت (JSON نامعتبر + رشتهٔ خالی) = ۲۲ سناریو

روش: بعد از یک لود اولیهٔ سالم (تا مقادیر seed بنشینند)، هر کلید عمداً یا به `'{not valid json!!'` یا به `''` تغییر داده شد، صفحه reload شد، و بعد از ۱.۵ ثانیه سلامت DOM چک شد.

```
هر ۲۲ سناریو: pageErrors=0  bodyHasContent=true  toolsGridChildren=10  cryptoListChildren>0
```

**نتیجه: بدون استثنا، هیچ کلید خراب‌شده‌ای کل newtab را کرش نداد.** گرید ابزارها (۱۰ آیتم، مستقل از localStorage) و لیست قیمت‌ها (۱۲-۱۸ ردیف، بسته به موفقیت CORS در همان اجرا) در هر ۲۲ حالت رندر شدند. این با الگوی `try { JSON.parse(localStorage.getItem(K) || '{}') } catch (e) {}` که در سرتاسر کد (هر ۱۱ کلید) دیده شد، هم‌خوان است — هرجا JSON.parse با ورودی خراب شکست می‌خورد، catch خالی مقدار پیش‌فرض را جایگزین می‌کند، نه اینکه exception را propagate کند.

**این دقیقاً برخلاف نگرانی صریح تسک بود** («اگر [خرابی یک کلید باعث کرش کل newtab شود] این یک باگ معماری جدی است») — خوشبختانه چنین باگی پیدا نشد؛ معماری فعلی در برابر خرابی داده مقاوم است.

## تست اشباع Quota

```json
{
  "fillResult": { "mbWritten": 4, "threwOnWrite": { "name": "QuotaExceededError", "message": "..." } },
  "pageErrorsThrown": 0,
  "domHealth": { "bodyHasContent": true, "toolsGridChildren": 10 }
}
```

روش: با یک اسکریپت جدا (نه اپلیکیشن)، چانک‌های ۱ مگابایتی نوشته شدند تا مرورگر واقعاً `QuotaExceededError` پرتاب کند (در origin از نوع `file://` این اتفاق حوالی ۴ مگابایت افتاد — سقف واقعی روی یک `chrome-extension://` ممکن است عدد دیگری باشد، ولی خودِ رفتار برنامه در برابر «فضای پر» است که اینجا تست شد، نه عدد دقیق سقف مرورگر). بعد از پر شدن کامل quota، اپ واقعی روی همان صفحه reload شد: **باز هم بدون کرش**، چون نوشتن‌های خود اپ هم داخل `try{...}catch(e){}` هستند (مثلاً `newtab.js:265`: `try { localStorage.setItem(PERSIST_KEY, ...) } catch (e) {}`).

## نکتهٔ جانبی دربارهٔ ریسک واقعی حجم (اسکرین‌شات ژورنال)

`js/journal.js` تنها بخشی است که واقعاً می‌تواند حجم بزرگ تولید کند — معاملات با اسکرین‌شات base64 پیوست‌شده در همان کلید `ib_journal_v1` ذخیره می‌شوند (نه جای دیگری). خودِ کد این ریسک را از قبل می‌شناسد و برایش راه‌حل دارد: در صورت شکست `setItem` به‌خاطر quota، کد (`js/journal.js`، حوالی خط ۹۹-۱۲۰) به‌صورت خودکار قدیمی‌ترین اسکرین‌شات‌ها را حذف می‌کند و فقط دادهٔ متنی معامله را نگه می‌دارد — این دقیقاً همان الگوی «مدیریت شده به‌جای کرش» است.
