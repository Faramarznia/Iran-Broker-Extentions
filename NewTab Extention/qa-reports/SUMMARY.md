## 🔴 ۳ مورد بحرانی‌ترین برای رفع قبل از merge

ترتیب بر اساس severity واقعی کشف‌شده، نه ترتیب تسک‌های بالا — مورد اول اصلاً بخشی از این ۷ تست نبود.

### ۱. محاسبهٔ P&L برای معاملات کریپتو در ژورنال فاجعه‌بار غلط است (فراتر از دامنهٔ این ۷ تست)

در حین گرفتن اسکرین‌شات برای تست RTL (۲)، یک معاملهٔ نمونهٔ BTC (ورود ۶۱,۲۰۰$، خروج ۶۳,۰۰۰$، حجم ۰.۱ لات) در جدول تاریخچهٔ ژورنال **P&L برابر با ۱۸,۰۰۰,۰۰۰,۰۰۰+$ (۱۸ میلیارد دلار)** نشان داد — و همین عدد کل کارت‌های KPI صفحهٔ آمار (بهترین معامله، P&L کل، میانگین سود) را هم آلوده کرد.

**علت ریشه‌ای** — `js/journal.js:209-215`:
```js
function pipSizeFor(symbol) {
  var s = (symbol || '').toUpperCase();
  if (s.indexOf('JPY') >= 0) return 0.01;
  if (s.indexOf('XAU') >= 0) return 0.1;
  if (s.indexOf('XAG') >= 0) return 0.01;
  return 0.0001;   // ← هیچ حالتی برای کریپتو (BTC/ETH/...) وجود ندارد
}
```
برای نمادهایی که در فهرست فوق نیستند (هر نماد کریپتویی)، اندازهٔ پیپ پیش‌فرض فارکس (۰.۰۰۰۱) استفاده می‌شود. برای BTC با تفاوت قیمت ۱۸۰۰ دلاری، این یعنی `۱۸۰۰ / ۰.۰۰۰۱ = ۱۸,۰۰۰,۰۰۰` «پیپ» به‌جای یک عدد معنادار، که بعد در `pnlAmount = pips * pipVal * lot` (خط ۲۵۴) ضرب می‌شود و به میلیاردها دلار می‌رسد.

**تأثیر**: هر معاملهٔ کریپتویی ثبت‌شده در ژورنال (نه فقط BTC — هر نماد خارج از JPY/XAU/XAG) آمار P&L، نرخ موفقیت، Profit Factor، منحنی رشد سرمایه و همهٔ گزارش‌های تحلیلی را کاملاً بی‌اعتبار می‌کند. این دقیقاً یک ویژگی محصولی (ژورنال معاملاتی) را که ادعای اصلی «تحلیل معاملات» دارد، برای بخش قابل‌توجهی از کاربران هدف (معامله‌گران کریپتو) بی‌فایده/گمراه‌کننده می‌کند.

**پیشنهاد اصلاح**: افزودن حالت برای نمادهای کریپتو در `pipSizeFor`/`pipValueFor` (مثلاً محاسبهٔ مستقیم `(exit-entry)*lot*direction` بدون مفهوم «پیپ» برای کریپتو، یا یک اندازهٔ پیپ متناسب با مقیاس قیمت نماد).

اسکرین‌شات مدرک: `screenshots/rtl-journal-history-table.png` (نسخهٔ اول قبل از حذف BTC از seed).

### ۲. Failover دو-میزبانهٔ TGJU بودجهٔ زمانی واقعی را به ۱۸ ثانیه می‌رساند (تست ۴)

اثبات‌شده با اجرای واقعی: وقتی هر دو میزبان TGJU (`call2`/`call3`) بی‌پاسخ بمانند، UI تا **~۱۸ ثانیهٔ واقعی** (نه ۹ ثانیه‌ای که یک نگاه سطحی به کد نشان می‌دهد) در حالت لودینگ می‌ماند، چون دو تلاش ۹۰۰۰ میلی‌ثانیه‌ای به‌صورت **متوالی**، نه همزمان، اجرا می‌شوند (`newtab.js:1030-1042`). برای مخاطب هدف این محصول (معامله‌گران ایرانی، که اغلب با اتصال کند/ناپایدار سروکار دارند)، این می‌تواند تجربهٔ رایج باشد نه یک حالت لبه‌ای نادر.

### ۳. برچسب‌های نمودار «توزیع R:R» با ترتیب معکوس نمایش داده می‌شوند (تست ۲)

با یک آزمایش کنترل‌شدهٔ pixel-diff اثبات شد: `ctx.direction` روی canvas از `<html dir="rtl">` به ارث می‌رسد و رشتهٔ برچسب `'۰–۰.۵'` (قصد: «۰ تا ۰.۵») را به‌صورت بصری «۰.۵–۰» (معکوس) رندر می‌کند. اصلاح یک‌خطی (`ctx.direction = 'ltr'` در `setupCanvas()`، `js/journal.js:1373`) کل مشکل را حل می‌کند.

## یافته‌های دیگر (severity متوسط/پایین، جزئیات در گزارش‌های مربوطه)

- تقویم‌های heatmap در ژورنال هفته را یکشنبه شروع می‌کنند، برخلاف تقویم اصلی هاب که درست شنبه‌شروع است (تست ۲).
- ادعای PRD «تمام ویجت‌ها fallback استاتیک دارند» فقط برای تب کریپتو صادق است — فارکس و بازار ایران فقط پیام خطا نشان می‌دهند، بدون fallback (تست ۳).
- ۱۲ از ۱۶ فراخوان fetch در کل کد زنده هیچ AbortController/timeout ندارند — می‌توانند تا ابد در حالت لودینگ گیر کنند اگر سرور مقصد hang کند (تست ۴).
- ادعای PRD دربارهٔ breakpoint های «۱۱۰۰px→۷۰۰px» ساده‌سازی‌شده است؛ کد واقعی ۸ breakpoint متفاوت دارد (تست ۱، بدون تأثیر منفی روی نتیجهٔ تست).

## نکات مثبت قابل‌توجه (برای اینکه فقط باگ‌ها دیده نشوند)

- **صفر uncaught exception** در کل ۷ تست، حتی زیر شبیه‌سازی سنگین قطعی/hang شبکه و خرابی عمدی هر ۱۱ کلید localStorage.
- معماری try/catch دور تمام خواندن/نوشتن‌های localStorage واقعاً مقاوم است — تأیید شده با ۲۲ سناریوی خرابی + تست quota.
- failover واقعی TGJU (`call2`→`call3`) واقعاً کار می‌کند، فقط سرعتش کندتر از حد انتظار است.
- رندر اولیهٔ صفحه (FCP) زیر ۳۰۰ میلی‌ثانیه است، کاملاً مستقل از وضعیت شبکه/API — دقیقاً طبق طراحی async-first.
- تور خوش‌آمدگویی و تشخیص RTL جدول‌ها/تقویم اصلی هاب/نمودار equity curve همگی درست پیاده‌سازی شده‌اند.
